# Database Architecture

TitanCore uses a hybrid database architecture:

- PostgreSQL stores durable business data.
- Redis stores realtime and temporary gameplay state.
- RabbitMQ transports asynchronous work only.

PostgreSQL is the persistent source of truth. Redis is the realtime source of active state during gameplay. RabbitMQ must never be used inside the attack loop.

## PostgreSQL Standards

Common columns for mutable business tables:

| Column | Type | Rule |
| --- | --- | --- |
| `id` | `uuid` | Primary key, generated by application or database |
| `created_at` | `timestamptz` | Not null, default `now()` |
| `updated_at` | `timestamptz` | Not null, default `now()`, updated by application |
| `deleted_at` | `timestamptz` | Nullable, soft delete marker when needed |
| `version` | `bigint` | Optimistic locking for mutable aggregate roots |

Use `deleted_at` for user-owned and admin-managed data that must be recoverable or auditable. Avoid soft delete for append-only history tables.

## Table Definitions

### Authentication

#### `users`

Purpose: Stores account identity and login credentials.

| Column | Type | Constraints |
| --- | --- | --- |
| `id` | `uuid` | PK |
| `email` | `varchar(320)` | not null, unique |
| `username` | `varchar(32)` | not null, unique |
| `password_hash` | `varchar(255)` | nullable for OAuth-only accounts |
| `status` | `varchar(24)` | not null, default `ACTIVE`, check `ACTIVE,BANNED,LOCKED,DELETED` |
| `role` | `varchar(24)` | not null, default `PLAYER`, check `PLAYER,ADMIN` |
| `email_verified_at` | `timestamptz` | nullable |
| `last_login_at` | `timestamptz` | nullable |
| `version` | `bigint` | not null, default `0` |
| `created_at` | `timestamptz` | not null |
| `updated_at` | `timestamptz` | not null |
| `deleted_at` | `timestamptz` | nullable |

Indexes:

- Unique `users_email_uq` on `lower(email)` for login.
- Unique `users_username_uq` on `lower(username)` for profile lookup.
- `users_status_idx` for admin moderation screens.

#### `refresh_tokens`

Purpose: Stores refresh token family state for JWT rotation.

| Column | Type | Constraints |
| --- | --- | --- |
| `id` | `uuid` | PK |
| `user_id` | `uuid` | FK `users(id)`, not null |
| `token_hash` | `varchar(255)` | not null, unique |
| `token_family_id` | `uuid` | not null |
| `expires_at` | `timestamptz` | not null |
| `revoked_at` | `timestamptz` | nullable |
| `replaced_by_token_id` | `uuid` | nullable FK `refresh_tokens(id)` |
| `created_at` | `timestamptz` | not null |

Indexes:

- `refresh_tokens_user_idx` on `user_id`.
- `refresh_tokens_family_idx` on `token_family_id`.
- `refresh_tokens_expires_idx` on `expires_at` for cleanup.

Cascade: Restrict user deletion; accounts should be soft-deleted.

Indexes:

- `audit_logs_actor_created_idx` on `(actor_user_id, created_at desc)`.
- `audit_logs_target_idx` on `(target_type, target_id, created_at desc)`.

## Cascade And Orphan Strategy

- Use restrictive FKs for identity, payments, inventory, and audit data.
- Avoid physical cascade delete for player-owned data.
- Use soft delete for users, player profiles, guilds, items, and bosses.
- Use append-only tables for login history, battle history, damage logs, payment transactions, and audit logs.
- Orphan removal is allowed only for child definition rows like boss phases or boss skills when the parent boss definition is intentionally removed in an admin-only migration.

## Transaction Strategy

- Keep transactions short.
- Use `READ COMMITTED` by default.
- Use optimistic locking for mutable aggregate roots such as users and player profiles.
- Use idempotency keys for payment, reward, and async job results.
- Use explicit locking only for rare administrative operations.

## Flyway Strategy

Migration location:

```text
backend/src/main/resources/db/migration
```

Naming convention:

```text
V2026_07_22_001__create_auth_tables.sql
V2026_07_22_002__create_player_tables.sql
V2026_07_22_003__create_item_inventory_tables.sql
```

Rules:

- Versioned migrations are immutable after merge.
- Use repeatable migrations only for views or reference-data refreshes.
- Rollback is forward-only: create a new corrective migration.
- Test migrations on a clean database and an upgraded database.
- Do not generate migration scripts until schema approval.

## Security

- SQL injection is prevented with JPA parameter binding and no string-concatenated SQL.
- Passwords are stored as slow hashes only.
- Refresh tokens are stored as hashes only.
- Sensitive payment metadata must be minimized and masked in logs.
- Audit logs must not contain raw secrets.
- PII should be limited and encrypted later if legal/compliance needs require it.
