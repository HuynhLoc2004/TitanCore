# Database Architecture

TitanCore uses a hybrid database architecture:

- PostgreSQL stores durable business data.
- Redis stores realtime and temporary gameplay state.
- RabbitMQ transports asynchronous work only.

PostgreSQL is the persistent source of truth. Redis is the realtime source of active state during gameplay. RabbitMQ must never be used inside the attack loop.

## PostgreSQL Standards

Common columns for mutable business tables:

| Column | Type | Rule |
| --- | --- | --- |
| `id` | `uuid` | Primary key, generated by application or database |
| `created_at` | `timestamptz` | Not null, default `now()` |
| `updated_at` | `timestamptz` | Not null, default `now()`, updated by application |
| `deleted_at` | `timestamptz` | Nullable, soft delete marker when needed |
| `version` | `bigint` | Optimistic locking for mutable aggregate roots |

Use `deleted_at` for user-owned and admin-managed data that must be recoverable or auditable. Avoid soft delete for append-only history tables.

#### `reward_claims`

Purpose: Tracks reward ownership and claiming.

| Column | Type | Constraints |
| --- | --- | --- |
| `id` | `uuid` | PK |
| `reward_id` | `uuid` | FK `rewards(id)`, not null |

Indexes:

- `reward_claims_player_status_idx` on `(player_id, status, created_at desc)`.
- Unique `reward_claims_idempotency_uq` on `(player_id, reward_id, source_type, source_id)` for exactly-once logical reward processing.

The `source_id` is a durable event or aggregate identifier, such as `battle_room_id`, `payment_transaction_id`, or a durable outbox `aggregate_id`. It is non-null because PostgreSQL unique constraints allow multiple nulls, which would break reward idempotency during RabbitMQ redelivery.

Reward transaction rule:

- Create or confirm reward claim.
- Mutate inventory if the reward grants items.
- Insert immutable reward ledger entry.
- Commit all reward side effects atomically.

#### `reward_ledger`

Purpose: Immutable audit trail for every granted reward.

| Column | Type | Constraints |
| --- | --- | --- |

| `metadata` | `jsonb` | not null, default `{}` |
| `created_at` | `timestamptz` | not null |

- Unique `reward_ledger_claim_grant_uq` on `(reward_claim_id, grant_key)`.

Deterministic `grant_key` formats:

- `ITEM:{itemId}`
- `COSMETIC:{itemId}`
- `CURRENCY:{currencyCode}`

- `outbox_events_unpublished_idx` on `(next_attempt_at, occurred_at)` where `published_at is null`.
- `outbox_events_aggregate_idx` on `(aggregate_type, aggregate_id, occurred_at desc)`.

Rules:

- Battle completion and reward event creation occur in one transaction.
- Payment state update and payment event creation occur in one transaction.
- RabbitMQ publishers read unpublished outbox rows and mark `published_at` only after successful publish.
- Poll unpublished rows where `published_at is null` and `next_attempt_at <= now()`.
- Poll in ordered batches by `(next_attempt_at, occurred_at)`.
- Use PostgreSQL `FOR UPDATE SKIP LOCKED` when multiple publishers run.
- Mark `published_at` only after RabbitMQ publisher confirmation.
- Delivery remains at-least-once, so consumers remain idempotent.

## Currency And Inventory Consistency

Currency is deferred to the Game Economy phase.

Phase 2.5 must not implement player currency balances, currency mutation, or currency ledgers unless the Game Economy scope is explicitly approved. Until then, rewards that mention currency remain design placeholders and must not be executable economy behavior.

Item ownership model:

- Stackable items use one `inventory_items` row per `(inventory_id, item_id)` with `quantity > 0`.
- Unique/non-stackable items use one row per owned item with `quantity = 1`.
- No database uniqueness rule for stackable ownership is approved yet.
- Stackable and unique-item enforcement is deferred to the explicitly approved Inventory/Game Economy implementation design.
- Phase 2.5 must not invent this constraint.

## Cascade And Orphan Strategy

- Use restrictive FKs for identity, payments, inventory, and audit data.
- Avoid physical cascade delete for player-owned data.
- Use soft delete for users, player profiles, guilds, items, and bosses.
- Use append-only tables for login history, battle history, damage logs, payment transactions, and audit logs.
- Orphan removal is allowed only for child definition rows like boss phases or boss skills when the parent boss definition is intentionally removed in an admin-only migration.

## Transaction Strategy

- Keep transactions short.
- Use `READ COMMITTED` by default.
- Use optimistic locking for mutable aggregate roots such as users and player profiles.
- Use idempotency keys for payment, reward, and async job results.
- Use explicit locking only for rare administrative operations.

Battle finalization strategy:

- Redis finalization locks are optimization only.
- PostgreSQL durable completion state is the final authority.
- Updating a `battle_rooms` row from `ACTIVE` to `COMPLETED` must be conditional and idempotent.
- Battle lifecycle check:
  - `WAITING`: `started_at` and `ended_at` are null.
  - `ACTIVE`: `started_at` is not null and `ended_at` is null.
  - `COMPLETED` or `CANCELLED`: `ended_at` is not null.
- Finalization must use a conditional update from `ACTIVE` to `COMPLETED`.
- Only the transaction that updates one `battle_rooms` row may create the completion outbox event.
- If Redis is lost before durable completion, the MVP policy is cancel-and-compensate; do not claim deterministic active battle reconstruction.

## Flyway Strategy

Migration location:

```text
backend/src/main/resources/db/migration
```

Naming convention:

```text
V2026_07_22_001__create_auth_tables.sql
V2026_07_22_002__create_player_tables.sql
V2026_07_22_003__create_item_inventory_tables.sql
```

Rules:

- Versioned migrations are immutable after merge.
- Use repeatable migrations only for views or reference-data refreshes.
- Rollback is forward-only: create a new corrective migration.
- Test migrations on a clean database and an upgraded database.
- Do not generate migration scripts until schema approval.

## Security

- SQL injection is prevented with JPA parameter binding and no string-concatenated SQL.
- Passwords are stored as slow hashes only.
- Refresh tokens are stored as hashes only.
- Sensitive payment metadata must be minimized and masked in logs.
- Audit logs must not contain raw secrets.
- PII should be limited and encrypted later if legal/compliance needs require it.
