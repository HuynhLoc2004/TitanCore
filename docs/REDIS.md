# Redis Architecture

Redis stores temporary, realtime, and low-latency data. PostgreSQL remains the durable source of truth.

## Key Design

| Data | Key Format | Structure | TTL | Update Strategy | Eviction |
| --- | --- | --- | --- | --- | --- |
| Boss HP | `battle:room:{roomId}:boss:hp` | string integer | Room lifetime + 10m | Atomic decrement via Lua | Expire after battle |
| Boss damage | `battle:room:{roomId}:damage` | sorted set | Room lifetime + 10m | `ZINCRBY playerId damage` after server validation | Expire after battle |
| Active battle room | `battle:room:{roomId}` | hash | Room lifetime + 10m | Hash update on lifecycle events | Expire after battle |
| Room players | `battle:room:{roomId}:players` | set | Room lifetime + 10m | Add/remove on join/disconnect | Expire after battle |
| Online presence | `presence:player:{playerId}` | string or hash | 90s sliding | Refresh on heartbeat | Expire |
| Online players by shard | `presence:shard:{shardId}:players` | sorted set | Reconciled | Score is last heartbeat epoch millis | Remove stale scores periodically |
| Player socket map | `ws:player:{playerId}` | hash | 2m sliding | Refresh on heartbeat | Expire |
| Socket player map | `ws:socket:{socketId}` | string | 2m sliding | Refresh on heartbeat | Expire |
| Attack cooldown | `cooldown:attack:{playerId}` | string | Cooldown duration | `SET NX PX` | Expire |
| Temporary buffs | `buff:{playerId}:{buffId}` | hash | Buff duration | Set on buff apply | Expire |
| Session cache | `session:{sessionKey}` | hash | Access token/session TTL | Refresh on activity | Expire |
| Rate limiter | `rate:{scope}:{subject}` | counter | Window duration | Increment with expiry | Expire |
| Realtime ranking | `leaderboard:{seasonId}` | sorted set | Season + 1d | `ZINCRBY playerId score` | Expire after snapshot |
| JWT blacklist | `jwt:blacklist:{jti}` | string | Token remaining TTL | Set on revoke/logout | Expire |

## Atomicity

Critical gameplay updates should use Lua scripts or Redis transactions:

```text
validate boss alive
validate room is active
validate cooldown
validate attackId has not been processed
apply server-calculated damage
update player damage sorted set
increment battle sequence
return new boss hp, player rank data, and battle sequence
```

## Atomic Attack Contract

- The server calculates and validates final damage.
- The client sends attack intention only and never provides trusted final damage.
- Each attack includes an `attackId` generated by the client and scoped to `(roomId, playerId)`.
- Redis stores processed attack IDs with a short TTL using `attack:{roomId}:{playerId}:{attackId}` to reject duplicates.
- The atomic script validates cooldown, room membership, active room status, and boss-life state before applying damage.
- HP and damage ranking update in the same atomic operation.
- The script increments `battle:room:{roomId}:seq`.
- Broadcast events include the battle sequence so clients can reconcile missed or out-of-order messages.
- If boss HP reaches zero, the script marks a completion candidate; finalization is handled once by the server.

## Battle Completion And Recovery

One-time completion uses a Redis lock:

```text
SET battle:room:{roomId}:finalizing serverId NX PX 30000
```

The winner of the lock reads final Redis state and persists durable completion data to PostgreSQL. Completion must be idempotent through a durable PostgreSQL unique key on `battle_room_id`.

Redis crash recovery strategy:

- Active battle rooms are reconstructable from PostgreSQL `battle_rooms` and recent durable snapshots.
- Realtime per-hit state may be lost during a Redis crash unless snapshotting has already captured it.
- MVP policy: cancel or safely finalize affected active rooms with a system status and compensate players through auditable rewards if needed.
- Future hardening: periodic compact battle snapshots can be persisted asynchronously outside the attack loop.

## Presence Strategy

Presence is heartbeat-based, not permanent.

- WebSocket service refreshes `presence:player:{playerId}` on heartbeat.
- Expired presence means the player is considered offline.
- `presence:shard:{shardId}:players` is reconciled by removing stale scores older than the heartbeat timeout.
- PostgreSQL `user_sessions` stores durable session history, but Redis determines realtime online presence.

## Persistence

Redis is optimized for realtime state, not durable truth. Battle summaries, rewards, and rankings are persisted asynchronously after battle completion.

## Memory Strategy

- Use TTL on battle-specific keys.
- Avoid unbounded lists for gameplay events.
- Store compact values.
- Prefer sorted sets for leaderboards.
- Use periodic cleanup for stale online/session mappings.
